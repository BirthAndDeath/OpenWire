## 二、多设备消息投递架构方案

### 2.1 现状分析

当前架构：**1 身份 = 1 设备**

| 组件 | 现状 | 问题 |
|------|------|------|
| ML-KEM 密钥对 | 每次启动/切换身份重新生成 | 不同设备无法解密同一消息 |
| PeerID | 每次启动重新生成 | 同一身份在不同设备上有不同 PeerID |
| DHT 缓存 | `set_pubkey_peerid` 覆盖旧映射 | 只能存储一个 PeerID 对应一个身份 |
| 消息路由 | 直接发送到单个 PeerID | 不知道对方有多个设备 |

### 2.2 目标架构

```
发送者                         接收者身份 (ML-DSA 公钥)
  │                                │
  │  1. DHT 查询获取所有设备        │
  │  ┌─────────────────────┐      │
  │  │ 设备 A (PeerID_A)   │      │  ← 随机选择一台
  │  │ 设备 B (PeerID_B)   │      │
  │  │ 设备 C (PeerID_C)   │      │
  │  └─────────────────────┘      │
  │                                │
  │  2. 发送消息到设备 A           │
  │ ──────────────────────────────>│
  │                                │
  │                   3. 设备 A 通过
  │                  NetEvent 同步
  │                   ┌────────┐  │
  │                   │ 设备 B │  │
  │                   │ 设备 C │  │
  │                   └────────┘  │
```

**核心原则**：发送者只负责投递到**一台**接收设备，设备间同步由接收方负责。

```rust
/// 设备间消息同步：接收设备将消息推送到同一身份的其他设备
SyncMessage {
    /// 发送者的 ML-DSA 公钥 hex（原始消息的发送者）

    /// 消息类型

    /// 原始消息的签名哈希（用于去重）
    original_hash: [u8; 32],
    /// 消息时间戳
    timestamp: u64,
},

/// 设备注册/心跳：通知其他设备自己的存在
DeviceAnnounce {
    /// 自己的 ML-DSA 公钥 hex（身份标识）
    mldsa_pubkey_hex: String,
    /// 自己的 PeerID
    peer_id: String,
    /// 自己的 ML-KEM 公钥（新设备可用此密钥加密同步数据）
    mlkem_pubkey_hex: String,
    /// 设备名称（用户可读）
    device_name: String,
},
```

### 2.4 多设备存储表

```sql
-- 设备表：记录同一身份下的所有设备
CREATE TABLE devices (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    -- 所属身份的 ML-DSA 公钥 hex
    owner_identity_id TEXT NOT NULL,
    -- 设备的 PeerID（Base58 编码）
    peer_id TEXT NOT NULL UNIQUE,
    -- 设备的 ML-KEM 公钥 hex
    mlkem_pubkey_hex TEXT NOT NULL,
    -- 设备名称
    device_name TEXT NOT NULL DEFAULT '',
    -- 最后在线时间
    last_seen INTEGER NOT NULL DEFAULT (strftime('%s', 'now')),
    -- 是否信任此设备
    is_trusted INTEGER NOT NULL DEFAULT 1,
    FOREIGN KEY (owner_identity_id) REFERENCES identities(identity_id)
);

-- 消息同步状态：记录哪些消息已同步到哪些设备
CREATE TABLE message_sync_status (
    message_hash TEXT NOT NULL,
    target_device_id INTEGER NOT NULL,
    sync_status TEXT NOT NULL DEFAULT 'pending',  -- pending/synced/failed
    synced_at INTEGER,
    PRIMARY KEY (message_hash, target_device_id),
    FOREIGN KEY (target_device_id) REFERENCES devices(id)
);
```

### 2.5 DHT 缓存改造

```rust
// DhtCache 改为支持多 PeerID

pub struct DhtCache {
    // 原: HashMap<String, PeerId>  →  1:1
    // 改: HashMap<String, Vec<(PeerId, Instant)>>  →  1:N
    pubkey_peerids: Arc<DashMap<String, Vec<(PeerId, Instant)>>>,
    
    // 设备 ML-KEM 公钥（每个设备独立）
    device_mlkem_pubkeys: Arc<DashMap<PeerId, String>>,
}

impl DhtCache {
    /// 获取某身份的所有在线设备 PeerID
    pub fn get_peerids_by_pubkey(&self, pubkey: &str) -> Vec<PeerId>;
    
    /// 随机选择一个在线设备
    pub fn pick_random_device(&self, pubkey: &str) -> Option<PeerId>;
    
    /// 注册设备（不覆盖，追加）
    pub fn add_device(&self, pubkey: &str, peer_id: PeerId, ttl: Duration);
}
```

### 2.6 消息投递流程（改造后）

```
发送者 send_message:
  1. DHT 查询目标身份的所有设备 PeerID 列表
  2. 随机选择一个在线设备
  3. 用该设备的 ML-KEM 公钥加密消息
  4. 发送到选中的 PeerID
  5. 不关心其他设备

接收设备 A 收到消息:
  1. 用本地 ML-KEM 私钥解密
  2. 存入本地 messages 表
  3. 查询本地 devices 表，获取其他设备列表
  4. 对每个在线设备 B/C：
     a. 用设备 B 的 ML-KEM 公钥加密消息
     b. 通过 NetEvent SyncMessage 推送
  5. 更新 message_sync_status 表

设备 B 收到 SyncMessage:
  1. 用本地 ML-KEM 私钥解密
  2. 检查 original_hash 是否已存在（去重）
  3. 存入本地 messages 表
  4. 发送 Ack 回设备 A
```
