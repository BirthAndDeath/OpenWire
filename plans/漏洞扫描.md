# OpenWire 仓库漏洞扫描报告

扫描类型：静态代码审计 + 构建验证
扫描范围：Rust 核心模块、Tauri 前端、Keyring/身份存储层
扫描时间：2026-07-22

## 1. 扫描结论摘要

本次扫描以代码审计和现有构建检查为主，结论如下：

- 当前仓库可以通过基础构建检查：`cargo check --workspace` 已完成，`npm run check` 也为 0 错误。
- 但仍然存在若干“可触发”的安全与功能缺陷，主要集中在文件传输、网络事件处理、DHT 缓存和身份/密钥处理路径。
- 这些问题不会全部导致立即被利用，但在异常输入、网络分区、重试场景或高负载下，容易引发服务异常、消息丢失、文件写入越界或进程崩溃。

| 类型 | 级别 | 数量 | 说明 |
|---|---|---:|---|
| 安全类问题 | 高/中 | 3 | 包括路径穿越、外部输入导致 panic、密钥/身份处理的异常路径风险 |
| 功能实现问题 | 中/低 | 5 | 包括消息丢失、缓存失效、下载流程异常、Android 链路未验证 |

---

## 2. 安全类问题

### 2.1 高危：下载文件路径可被外部文件名绕过，触发路径穿越

- 位置： [openwire_core/src/core/file_transfer.rs](openwire_core/src/core/file_transfer.rs)
- 证据：完成下载时使用 `self.downloads_dir().join(filename)`，其中 `filename` 来自对端或传输上下文。
- 风险：如果远端传入的文件名为 `../../somefile` 或包含目录分隔符，可能导致文件被写到下载目录之外，覆盖本地其他文件，甚至破坏应用正常工作目录。
- 影响：不仅是安全问题，也会直接导致功能异常，例如下载文件被写到错误路径、覆盖系统文件或触发后续读取失败。
- 建议：对下载文件名进行白名单/规范化处理，禁止 `..`、绝对路径、控制字符和路径分隔符；只允许安全的基础文件名。

### 2.2 高危：外部输入或异常数据可触发 panic，导致服务崩溃

- 位置： [openwire_core/src/core/event_loop.rs](openwire_core/src/core/event_loop.rs)、[openwire_core/src/core/file_transfer.rs](openwire_core/src/core/file_transfer.rs)
- 证据：代码中存在类似 `&mldsa_pubkey_hex[..16]`、`&file_id_hex[..16]` 以及 `unwrap()` 的直接使用；这些操作假设输入长度足够长且格式正确。
- 风险：当对端发送的公钥、文件 ID、PeerID 或消息字段格式异常时，代码可能直接 panic，导致核心线程退出或整个应用崩溃。
- 影响：会形成拒绝服务（DoS）场景，特别是在网络分区、恶意节点、异常消息或旧版本节点互通时更容易触发。
- 建议：将所有字符串切片、长度判断和反序列化改为显式校验并返回错误，而不是直接 panic 或 unwrap。

### 2.3 中危：密钥/身份存储路径在异常情况下可能出现不稳定的恢复行为

- 位置： [rootcell/src/identity.rs](rootcell/src/identity.rs)
- 证据：私钥加密文件和 Keyring 组合使用，但在 keyring 不可用、主密钥不存在、密文损坏或解密失败时，代码主要依赖返回 `None` 或 warning，并没有强制性的回滚/隔离策略。
- 风险：在异常输入或平台兼容性异常时，身份恢复链路容易进入“半失败”状态，可能导致用户身份不可用、密钥文件残留或后续加载失败。
- 影响：会表现为“看起来能启动，但实际无法恢复身份”或“某些身份无法加载”的功能性故障。
- 建议：为身份恢复流程增加明确的状态机和错误分支，区分“密钥缺失”“密钥损坏”“Keyring 不可用”等场景，并给出可恢复的处理方式。

## 3. 功能实现问题

### 3.1 中危：DHT 缓存使用 `lock().unwrap()`，一旦 Mutex 被污染会导致缓存逻辑失效

- 位置： [openwire_core/src/p2p/dht_cache.rs](openwire_core/src/p2p/dht_cache.rs)
- 证据：多个地方使用 `self.pubkey_peerid.lock().unwrap()`、`self.mlkem_pubkeys.lock().unwrap()` 等。
- 问题：如果之前某个线程 panic 导致 Mutex 进入 poisoned 状态，后续所有 DHT 查询/写入都会直接失败，进而破坏 peer discovery、好友发现和身份映射。
- 影响：会导致“好友上线后仍然发现不到”“消息发送重试失效”的功能问题。
- 建议：改为 `lock().unwrap_or_else(|e| { ... })` 或使用更稳健的并发容器，避免单次 panic 影响整个缓存系统。

### 3.2 中危：非阻塞消息发送可能导致命令或消息被静默丢弃

- 位置： [openwire_core/src/core/event_loop.rs](openwire_core/src/core/event_loop.rs)、[openwire_core/src/core/message_ops.rs](openwire_core/src/core/message_ops.rs)
- 证据：代码中大量使用 `try_send(...)`，并忽略发送失败。
- 问题：当事件队列满载、Actor 处理迟缓或核心线程暂时不可用时，命令会被直接丢弃，而不是进入重试/缓冲流程。
- 影响：会出现消息发送成功“看起来已提交，但实际没进入网络层”的现象，尤其在高并发或网络抖动时更明显。
- 建议：将这类发送改为显式错误处理与重试/降级策略；必要时引入缓冲队列或 backpressure。

### 3.3 中危：文件名冲突处理依赖 `unwrap()`，在极端路径场景下可能中断下载流程

- 位置： [openwire_core/src/core/file_transfer.rs](openwire_core/src/core/file_transfer.rs)
- 证据：在生成备用文件名时，使用 `.find(...).unwrap()`。
- 问题：当目标目录中已存在大量同名文件、路径无效或文件系统状态异常时，备用文件名生成可能失败，导致整个下载完成逻辑报错。
- 影响：会出现“文件已下载但无法落盘”的现象，用户体验差且难以自动恢复。
- 建议：将备用文件名生成改为显式循环并在失败时返回错误，而不是依赖 `unwrap()`。

### 3.4 中危：配置初始化中的 `unwrap()` 逻辑存在隐含缺陷

- 位置： [openwire_core/src/coreconfig.rs](openwire_core/src/coreconfig.rs)
- 证据：`if path_to_log.is_none() { ... }` 之后仍然调用 `path_to_log.unwrap()`。
- 问题：这段逻辑在代码结构上是冗余且容易被后续修改打破；一旦条件判断变更，可能触发 panic。
- 影响：配置初始化在极少数路径下会失败，影响日志系统与调试能力。
- 建议：将其改成更直接的分支逻辑，避免无意义的 `unwrap()`。

### 3.5 中危：Android 目标链路未通过当前环境验证

- 位置： [openwire/package.json](openwire/package.json)
- 证据：终端中 `npm run tauri android dev` 的执行结果为非 0 退出码。
- 问题：虽然桌面端和前端检查已通过，但 Android 开发链路没有在当前环境中被成功验证。
- 影响：Android 端功能可能存在构建、依赖或配置问题，导致发布前发现问题的成本高。
- 建议：把 Android 构建和运行链路纳入 CI，并在每次提交前做自动化验证。

---

## 4. 建议优先级

1. 先处理“路径穿越 + panic 输入校验”，这是最容易直接造成安全和稳定性问题的点。
2. 再处理“消息/命令发送的错误处理”，避免高负载时出现静默丢失。
3. 最后补齐“DHT 缓存、身份恢复和 Android 构建链路”的健壮性和自动化测试。

---

## 5. 结论

OpenWire 目前的基础构建是可用的，但从代码层面看，仍存在多处容易在真实使用场景中触发的稳定性和功能缺陷。尤其是文件传输路径处理、异常输入导致的 panic、消息队列丢弃和 DHT 缓存恢复路径，建议尽快纳入修复计划。

---

## 6. 修复计划

### 6.1 第一阶段：高优先级修复（建议 1-2 周内完成）

#### 1) 文件传输路径安全校验
- 目标：阻止下载路径穿越与异常文件名写入。
- 改动点：
  - 在 [openwire_core/src/core/file_transfer.rs](openwire_core/src/core/file_transfer.rs) 增加文件名规范化函数。
  - 禁止 `..`、绝对路径、路径分隔符、控制字符和空文件名。
  - 下载完成时统一使用安全落盘路径。
- 验收标准：
  - 传入 `../foo`、`/tmp/x`、`a/b` 等恶意名称时，系统拒绝写入并返回错误。
  - 正常文件名仍能正常下载。

#### 2) 消除 panic 弱点，改为显式错误处理
- 目标：避免异常输入造成核心线程崩溃。
- 改动点：
  - 在 [openwire_core/src/core/event_loop.rs](openwire_core/src/core/event_loop.rs) 和 [openwire_core/src/core/file_transfer.rs](openwire_core/src/core/file_transfer.rs) 中把 `unwrap()`、`[..]` 切片、`parse()` 等高风险调用替换为显式校验。
  - 对不合法输入返回 `CoreError` 或日志告警，而不是 panic。
- 验收标准：
  - 异常公钥、异常文件 ID 或异常消息结构不会导致核心线程退出。
  - 日志里能清晰看到错误原因。

#### 3) 完善消息/命令发送的错误处理
- 目标：避免高负载或队列阻塞时发生静默丢失。
- 改动点：
  - 将 [openwire_core/src/core/event_loop.rs](openwire_core/src/core/event_loop.rs) 及相关消息发送路径中的 `try_send` 失败情况纳入日志与重试策略。
  - 对关键消息（如好友上线通知、离线消息重试、DHT discover）增加降级处理。
- 验收标准：
  - 队列满载时，系统不会无声丢弃关键动作。
  - 可以通过日志判断是否触发了重试/降级。

### 6.2 第二阶段：稳定性与功能修复（建议 2-4 周内完成）

#### 4) 修复 DHT 缓存的异常恢复逻辑
- 目标：避免 Mutex 污染或缓存状态异常时影响整个发现链路。
- 改动点：
  - 在 [openwire_core/src/p2p/dht_cache.rs](openwire_core/src/p2p/dht_cache.rs) 中把 `lock().unwrap()` 改为更稳健的处理。
  - 增加缓存失效/重建逻辑，确保单次异常不会影响后续查询。
- 验收标准：
  - 某一项缓存操作失败后，其他缓存键仍可正常工作。
  - DHT 发现链路能在异常后自动恢复。

#### 5) 补齐身份恢复与密钥存储流程
- 目标：提高身份恢复的可控性和可诊断性。
- 改动点：
  - 在 [rootcell/src/identity.rs](rootcell/src/identity.rs) 中明确区分“密钥缺失”“密钥损坏”“Keyring 不可用”。
  - 增加失败后的回滚策略、清理策略和用户提示。
- 验收标准：
  - 用户在不同异常场景下能收到明确提示。
  - 某个身份文件损坏时不会影响其他身份的正常使用。

#### 6) 修复配置初始化中的隐式风险
- 目标：去除容易在后续修改时触发 panic 的代码。
- 改动点：
  - 在 [openwire_core/src/coreconfig.rs](openwire_core/src/coreconfig.rs) 中把 `unwrap()` 改为显式分支。
- 验收标准：
  - 配置初始化逻辑在不同输入下都能稳定返回结果。

### 6.3 第三阶段：工程化加固（建议持续推进）

#### 7) 建立自动化回归测试
- 目标：把漏洞修复变成长期可验证项。
- 建议内容：
  - 为文件名安全校验编写单元测试。
  - 为异常公钥/异常文件 ID 的错误处理编写回归测试。
  - 为 DHT 缓存和消息重试逻辑增加集成测试。

#### 8) 补齐 Android 构建与发布验证
- 目标：确保 Android 端可持续构建。
- 改动点：
  - 将 [openwire/package.json](openwire/package.json) 中的 Android 构建链路纳入 CI。
  - 每次提交运行 `npm run tauri android dev` 或对应构建任务。
- 验收标准：
  - CI 中能稳定通过 Android 构建检查。
  - 发布前不再依赖手工验证。

---

## 7. 建议执行顺序

1. 先做“路径安全校验 + panic 消除”，因为它们直接影响安全性与稳定性。
2. 再做“消息发送与 DHT 缓存健壮性”，改善真实网络环境下的功能可靠性。
3. 最后补“测试与 Android CI”，将修复成果固化为长期治理机制。
